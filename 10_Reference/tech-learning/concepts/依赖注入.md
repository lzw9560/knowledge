# 依赖注入（Dependency Injection）

## 类别
- 设计模式（控制反转 IoC 的实现方式）
- 多语言通用：Python（FastAPI/Dish）、Java（Spring）、TS（NestJS）、C#（.NET DI）

## 核心特性
- **依赖反转**：高层模块不直接创建低层模块的实例，由容器注入——解耦
- **构造器注入**：通过构造函数参数注入依赖（最推荐，便于测试）
- **接口抽象**：依赖声明为抽象接口（Protocol/ABC），运行时绑定具体实现——可替换
- **生命周期**：单例（singleton）/ 作用域（scoped）/ 瞬时（transient），容器管理实例化

## 与其他模式的对比
| 模式 | 谁创建依赖 | 测试难度 |
|---|---|---|
| 直接 new | 调用方 | 难（硬编码） |
| 服务定位器 | 调用方主动取 | 中（隐藏依赖） |
| 依赖注入 | 容器注入 | 易（可 mock） |

## 在 Vibe-Research 中的使用
- [[10_Reference/investing/specs/archive/m0-foundation/S015-配置与基础设施|S015 config 分层]] — 配置拆分后通过 DI 注入到各 service，避免全局单例耦合
- [[10_Reference/[[tech-learning/frameworks/fastapi|FastAPI]] 的 `Depends()` 是 Python 原生 DI 实现——路由通过 `Depends` 注入 service / config
- [[10_Reference/[[tech-learning/architecture/清洁架构|清洁架构]][[清洁架构]] — DI 是"依赖反转"层级的运行时实现

## 反模式（避免）
- 在 service 内部直接 `import config`（硬编码依赖）——应通过构造器注入
- 在测试中无法替换依赖（如真实数据库连接）——说明 DI 缺失
