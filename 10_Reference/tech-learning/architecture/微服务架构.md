# 微服务架构

## 类别
- 分布式架构模式（Martin Fowler，2014）
- 与单体（monolith）的对比：微服务把系统拆成独立部署的小服务，单体是一个进程内多模块
- 与清洁架构的关系：微服务是**部署维度**的拆分，清洁架构是**单服务内**的分层——两者正交可叠加

## 核心特性
- **服务自治**：每个服务独立部署、独立数据库、独立技术栈
- **通过 API 通信**：HTTP/REST 或 RPC，或事件总线（见 [[10_Reference/tech-learning/architecture/事件驱动架构|事件驱动架构]]）
- **独立可扩展**：按服务负载单独扩容
- **去中心化治理**：服务间通过契约（contract）解耦，非共享数据库
- **成本**：分布式事务、网络延迟、运维复杂度上升（需 K8s / 服务网格）

## 微服务 vs 单体决策判据
| 维度 | 单体更优 | 微服务更优 |
|---|---|---|
| 团队规模 | < 5 人 | 多团队 |
| 部署频率 | 低 | 高（独立部署收益大） |
| 性能要求 | 单机够 | 需独立扩容热点 |
| 数据一致性 | 强一致 | 可接受最终一致 |

## 与 Vibe-Research 的关系
- Vibe-Research 当前是**单体**（FastAPI 单进程 + React 单页），团队规模 1 人，单体是正确选择
- [[10_Reference/investing/specs/archive/m0-foundation/S011-调度收口|S011 调度收口]] 在单体内用事件驱动解耦，是"单体 + 事件"的中间形态（参考 [[10_Reference/tech-learning/architecture/事件驱动架构|事件驱动架构]]）
- 关联项目 [[10_Reference/projects/active/TradingAgents|TradingAgents]] 是独立服务，与 Vibe-Research 通过共享数据源松耦合——这是**类微服务**边界
- S011 调度收口参考微服务的"服务边界"思想，但在单体内实现（事件总线而非网络）
